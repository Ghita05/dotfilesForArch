# Arch + Hyprland desktop: migrating from a custom Quickshell shell to Ambxst

## Machine

- ASUS Vivobook S 14 (S5406MA): Intel Core Ultra 7 (Meteor Lake), Intel Arc integrated graphics,
  Intel AX211 Wi-Fi, 16GB RAM, Samsung NVMe SSD
- Arch Linux, Hyprland 0.56.x configured in **Lua** (`hyprland.lua`), not `hyprland.conf`
- Root on LUKS + LVM. mkinitcpio hooks include `systemd`, `sd-vconsole`, `sd-encrypt`, `lvm2`
- **AZERTY** keyboard layout. Timezone `Africa/Casablanca`. Locales `en_US.UTF-8` and `fr_FR.UTF-8`
- Terminal: kitty. AUR helper: yay. Shell runtime: `quickshell-git` (provides `/usr/bin/qs`)
- Audio: PipeWire + wpctl, EasyEffects. Brightness: brightnessctl. Network: NetworkManager (no iwd)

## What this migration is

Replacing a hand-built Quickshell bar and control center with Ambxst
(https://github.com/Axenide/Ambxst). Both are installed. Ambxst runs and is themed.
Leftovers from the old setup still fire: old keybinds (Super+N, Super+Z, Super+Space),
the old bar still appears, and old autostarts are still in the Hyprland config.

## File map

| Path | What it is | Editable |
| --- | --- | --- |
| `~/dotfiles/` | git repo `Ghita05/dotfilesForArch`, source of truth | yes |
| `~/.config/hypr/hyprland.lua` | live Hyprland config | yes |
| `~/.config/ambxst/config/*.json` | Ambxst settings: bar, dock, desktop, notch, theme, workspaces, lockscreen, overview, system, performance, compositor | yes, then `ambxst reload` |
| `~/.local/share/ambxst/hyprland.lua` | **generated by the axctl daemon** | NO. Overwritten on every theme, gaps, or binds change |
| `~/.local/src/ambxst/` | Ambxst source clone | read only, reference for config schema |
| `~/.config/quickshell/` | the old hand-built shell | do not delete, disable only |
| `/usr/local/bin/ambxst`, `/usr/local/bin/axctl` | installed binaries | no |

Custom Hyprland binds go **below the `-- OVERRIDES` marker** in `~/.config/hypr/hyprland.lua`.
Never in the generated file.

Deployment is symlink-based via `install.sh`'s `ln -sfn` (confirmed: `~/.config/hypr`,
`~/.config/quickshell`, `~/.config/gtk-3.0` are all live symlinks into `~/dotfiles/.config/...`).
Editing the live file edits the dotfiles copy directly — they're the same inode. The one
exception is `~/.config/ambxst`: only `~/.config/ambxst/config/` is symlinked (to
`~/dotfiles/.config/ambxst/config/`); `binds.json` and `presets/` are deliberately
per-machine state, never copied into the dotfiles tree.

## Hyprland Lua API gotchas, learned the hard way

- Autostart uses `hl.exec_cmd(...)`. No `.dsp` on this one.
- Inside `hl.bind()`, dispatchers use `hl.dsp.exec_cmd(...)`.
- `hl.dsp.exec` does not exist. It throws a nil error that aborts the entire
  `hyprland.start` callback, taking the rest of the config with it.
- A nil or wrong-signature `hl.*` call anywhere in the file would abort the
  entire config load (not just the section it's in), so it's worth verifying
  new calls before writing them — but this was NOT what caused the
  2026-09-11 login failure (see the incident below). Don't assume a bad
  `hl.*` call without checking the actual log line first.
  - `hl.input` does not exist — `type(hl.input)` is `nil`. Input config goes
    through `hl.config({ input = {...} })`, not a dedicated function.
  - `hl.debug` does not exist — same, `nil`. Debug options (if any) would go
    under `hl.config({ debug = {...} })`, following the same pattern as input.
  - `hl.monitor({ name = ..., resolution = ... })` — `hl.monitor` itself
    exists, but its keys are `output=`/`mode=`/`position=`/`scale=`, not
    `name=`/`resolution=`. Calling it with the wrong keys throws
    `hl.monitor: 'output' field is required and must be a string` — a clean
    error, but still one that aborts the whole load.
  - **`hyprctl dispatch` on this build takes a Lua expression, not classic
    `.conf` dispatcher syntax.** Whatever text follows `dispatch` gets
    wrapped verbatim as `return hl.dispatch(<text>)` — so it has to be a
    complete, already-callable `hl.dsp.*` expression, not a bareword
    dispatcher name plus space-separated args the old way
    (`hyprctl dispatch workspace 2` fails with `')' expected near '2'`,
    and `hl.dsp.workspace` itself is a table — not callable — for
    rename/swap_monitors/toggle_special/change_id/move, so calling it
    directly fails too). Confirmed correct by reading the actual generated
    `~/.local/share/ambxst/hyprland.lua` (axctl's output, not guessed):
    switching workspace focus is `hl.dsp.focus`, e.g.
    `hyprctl dispatch 'hl.dsp.focus({workspace="2"})'`; moving the focused
    window to a workspace is `hl.dsp.window.move({workspace="2"})`; closing
    it is `hl.dsp.window.close()`; running a shell command is
    `hl.dsp.exec_cmd("command")`. General rule: quote a single, complete
    `hl.dsp.<category>.<method>(...)` or `hl.dsp.<method>(...)` call as one
    argument — never bareword dispatcher-plus-args. `hyprctl eval` follows
    the identical convention (see the verification tip right below) since
    both are the same Lua-eval mechanism under the hood.
  - **Before writing any new `hl.*` call into `hyprland.lua`, verify it first**
    with a non-destructive live check:
    `hyprctl eval "error('TYPE_IS:' .. type(hl.whatever))"` — the error text
    comes back on stderr with the real type (`hyprctl eval` does not print
    normal return values, only errors, so wrapping in `error()` is the way to
    see the result). `nil` means it doesn't exist; `function`/`table` means
    it does. This costs nothing and never touches the live config file.
- **"Creating the Error Overlay!" in `hyprland.log` is NOT evidence of an
  error.** It's a boilerplate component (`ErrorOverlay` manager) created on
  *every* startup, successful or not — confirmed by diffing a working
  session's log against a failed one; the line appears in both, at nearly the
  same position. Don't chase it as a lead. The real signal is the `[cfg]`
  line right before it: `[cfg] Using lua config found at <path>` (success)
  vs. `WARN: No config file found; attempting to generate.` (failure — the
  main config file genuinely didn't exist at that moment, not a parse error).
- **Incident, 2026-09-11**: a login landed in Hyprland's recovery config.
  Root cause (confirmed via `/run/user/1000/hypr/<instance>/hyprland.log`
  across the relevant session directories, cross-referenced with
  `~/.bash_history`): `mv hyprland.lua hyprland.lua.broken` immediately
  followed by a typo'd `ambxst install hyrpland` (should be `hyprland`) — the
  typo hit the CLI's `default:` case (prints "Unknown target", does nothing)
  rather than regenerating the file, so `~/.config/hypr/hyprland.lua` sat
  absent until the corrected `ambxst install hyprland` two commands later.
  Something restarted the Hyprland process in that exact window (not
  `hyprctl reload` — that re-parses in place and does not create a new
  `/run/user/1000/hypr/<instance>` directory, so it wasn't the trigger; what
  actually restarted the process was never conclusively identified). That
  restart found no config file at all and fell back to recovery. The config
  content itself (verified via MD5 against the last committed version) was
  never at fault. **Lesson: never leave `hyprland.lua` absent between `mv`ing
  it aside and regenerating it — write/generate the new one first, or do the
  swap as close to atomic as possible** (e.g. `ambxst install hyprland`
  targeting a temp path, then `mv` the old file aside and the new one into
  place in immediate succession, or just double-check the install command
  succeeded — `ls hyprland.lua` — before moving on).
- A successful `hyprctl reload` (and clean `hyprctl configerrors`) is **not**
  proof the config will survive an actual login. `hl.on("hyprland.start", ...)`
  only fires once, at real Hyprland startup — `hyprctl reload` re-parses the
  file but does not re-fire that event. Anything gated on it (autostart
  commands, first-run setup) is untested by a reload alone; it only gets
  exercised by an actual logout/login or a full Hyprland restart.
- Never use dpms-off for sleep. It has caused a lockout requiring a hard reboot.
  The correct pattern is `loginctl lock-session` plus hypridle's on-resume handler.
- **Known bug, confirmed non-fatal**: Ambxst's live theme-apply path
  (`modules/services/CompositorConfig.qml`, `applyCompositorConfigInternal`)
  double-serializes single-color (non-gradient) border colors. Root cause:
  `formatBorderColorForLua()` already wraps the single-color case in
  `JSON.stringify()` (correct — it's building a raw Lua string literal to
  embed), but the caller then puts that pre-quoted string into the `hlGeneral`
  object and the whole thing goes through `luaLiteral()`, which
  `JSON.stringify()`s string values *again* — producing `col.active_border =
  "\"rgb(9ccbfb)\""` instead of `"rgb(9ccbfb)"`. Confirmed via source read,
  and confirmed it's a real logic bug and not a torn/partial file read: the
  malformed text is a clean double-JSON-stringify artifact, not garbled or
  truncated the way a torn read would look.
  - **Confirmed confined to the live-eval hot-apply path, does NOT affect
    login.** The error surfaces via `hyprctl configerrors` wrapped as
    `return hl.config(...)` — that `return` prefix is `hyprctl eval`'s own
    wrapping convention, not how file-parse errors are reported (those cite
    file:line). This only fires when Ambxst is already running and a
    compositor-affecting setting changes live, dispatching an incremental
    `hl.config()` via `hyprctl eval` against the *already-running* compositor.
  - The static `~/.local/share/ambxst/hyprland.lua` — the one actually
    `loadfile()`'d at real Hyprland startup — is generated by a **separate**
    codebase: the `axctl` daemon (`/usr/local/bin/axctl`, Go, source not
    present on this machine). Confirmed via `strings` on the binary: its own
    format string is `active_border = "%s",` — single-wrapped, not the buggy
    QML path. The two code paths are independent; this bug cannot reach the
    file that matters at login.
  - A bad `hyprctl eval` call is non-fatal by construction anyway (confirmed
    repeatedly this session deliberately triggering malformed eval calls):
    it fails and logs, without touching the compositor's current, already-
    valid state. It's cosmetic at worst (the border color falls back to
    Hyprland's default until the next full reload/relaunch, since the eval
    call that would have set it failed).
  - Not deterministic on every reload — it's gated on the property actually
    *changing* (`onActiveBorderColorChanged` and friends), not on reload
    itself. Reproduced it once during real work, failed to reproduce twice
    afterward via `ambxst reload` and a manual `syncBorderColor` toggle test;
    exact trigger condition wasn't pinned down. Not investigated: axctl's own
    Go source (not available locally) could theoretically have an unrelated,
    different bug — the binary-strings evidence argues against it (correct
    single-wrap format string) but wasn't read directly.

## Suspend and hibernate

Suspend is currently **disabled on purpose** through a logind drop-in, because resume was
unreliable on this Meteor Lake machine. Re-enabling it is part of this migration and needs
real testing, not an assumption that a kernel update fixed it.

Hibernate has never been set up. It needs a swap device sized for RAM, a `resume=` kernel
parameter, and the `resume` hook in mkinitcpio, all complicated by the LUKS + LVM layout.
Treat this as its own project, not a quick toggle.

## Rules

- **Never run sudo.** Print the exact command and let me run it. This covers pacman and yay,
  systemctl, anything under `/etc`, mkinitcpio, and bootloader entries.
- Work on a git branch. Commit before anything risky.
- Read a config file before changing it. Do not assume the schema.
- Give me complete files, not fragments. No placeholders, no "rest unchanged" comments.
- Literal code only, no pseudocode.
- Use `\uXXXX` escapes instead of pasted Nerd Font glyphs.
- Explain the why for new QML concepts or architectural decisions, not just what to type.
- Changes that could cost me the session (Hyprland config, autostart, lockscreen, logind)
  get proposed and explained before they are applied.
